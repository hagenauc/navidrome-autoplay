# Navidrome Autoplay — Project Notes

> [!NOTE]
> This project, including all code, this repository, and these notes, was generated by an AI coding assistant. I guided it and tested the results on my own Navidrome server. The notes below describe how the project came together and what I saw on my setup. They aren't formal benchmarks.

## 1. Background

I run Navidrome at home and use Instant Mix a lot. I wanted mixes that stay close to the mood of the song I start with, change a bit each time, and move smoothly from song to song, more like what I was used to from streaming services.

I had been using **AudioMuse-AI**, which is a very capable project. For my particular library and my small server, I wanted to try something lighter that also makes use of my listening history (scrobbles and playlists). These notes cover what I looked into, what got built, and how it behaves for me.

## 2. Background reading: how streaming services approach autoplay

Here's my rough, simplified understanding of publicly available material on how large streaming services approach autoplay. It's only a summary and may not match how those systems actually work today.

```
[ Full Catalog / Local Library ]
               │
               ▼  Stage 1: Find candidates
    ┌───────────────────────────────┬───────────────────────────────┐
    │  Session & Playlist Graph     │   Acoustic & Vibe Embedding   │
    │  (Song2Vec / Session Markov)  │   (CLAP / MusiCNN / Timbre)   │
    └───────────────────────────────┴───────────────────────────────┘
               │  ~100–300 Candidates
               ▼  Stage 2: Rank against the session
    ┌───────────────────────────────────────────────────────────────┐
    │ Starting song                ◄── Keeps the overall mood       │
    │ Current song                 ◄── Keeps the next step smooth   │
    │ Familiar vs. new             ◄── Mix of known and new songs   │
    └───────────────────────────────────────────────────────────────┘
               │
               ▼  Stage 3: Transitions & variety
    ┌───────────────────────────────────────────────────────────────┐
    │ • Similar tempo (±10%, or half-time / double-time)            │
    │ • Compatible keys on the Camelot wheel                        │
    │ • Don't repeat the same artist or album too often             │
    └───────────────────────────────────────────────────────────────┘
               │
               ▼
     [ Next Track ]
```

### A. Ideas associated with Spotify
1. **Finding candidates in several ways:**
   * **Co-occurrence (`Song2Vec`-style):** Songs that often appear together in playlists or listening sessions are treated as similar, a bit like words that appear together in sentences.
   * **Audio embeddings:** Models trained on spectrograms describe things like energy, mood, and danceability.
2. **Balancing familiar and new (BaRT):**
   * Public talks describe a "bandit" approach that mixes mostly familiar choices with some new discoveries.
3. **Reacting to skips:**
   * Quick skips count as negative feedback and finished songs as positive.
4. **Smooth transitions:**
   * Keep tempo changes small (or use half-time / double-time) and prefer compatible keys.

### B. Ideas associated with Apple Music
1. **Editorial guidance:**
   * Recommendations are shaped by human-curated genres, scenes, and eras.
2. **Two reference points:**
   * If each song is picked only by comparing it to the previous one ($A \to B \to C \to D$), the mix can slowly drift somewhere unrelated. Comparing against both the **starting song** and the **current song** helps prevent that.
3. **Variety:**
   * Artists and albums aren't repeated too often in a single session.

## 3. What I wanted to improve for my library

These are things I noticed with my own library and listening habits. Other setups may see something quite different.

1. **Audio similarity alone didn't capture "scene" for my music.** My library has a lot of Austrian and German music (Volksmusik, Schlager, Austropop) next to pop, rock, and country. Songs that sound alike acoustically aren't always songs I'd want back to back.
2. **Mixes sometimes felt too narrow or wandered too far.** A single radius around the starting song is hard to tune for every library.
3. **I wanted to use my listening history.** My Navidrome database already had a few thousand scrobbles and several of my own playlists, and I wanted those to count.
4. **I wanted smoother transitions.** Tempo and key information seemed like an easy win when available.

## 4. What was built

It's written in Python using `numpy`, `scipy`, `scikit-learn`, `aubio`, and `mutagen`.

### Files

```
navidrome-autoplay/
├── config.py                  # Settings, weights, and ports
├── engine.py                  # Similarity map, session tracking, transition scoring
├── analyzer.py                # Multi-core BPM, key, and genre extraction
├── server.py                  # Flask API compatible with the AudioMuse-AI Navidrome plugin
├── service.sh                 # Helper script (start, stop, restart, status)
└── navidrome-autoplay.service # systemd unit file
```

`features.db` (the extracted audio features) is created locally at runtime and isn't part of the repository.

### Scoring
For candidate track $c$ and session history $H = [t_1, t_2, \dots, t_k]$, where $t_1$ is the starting song:

$$\text{Score}(c) = w_{\text{local}} S_{\text{svd}}(c, t_k) + w_{\text{macro}} S_{\text{svd}}(c, t_1) + w_{\text{art}} S_{\text{artist}}(c, t_k) + \text{Affinity}(c) + S_{\text{genre}}(c) + S_{\text{camelot}}(c) - P_{\text{fatigue}}(c, H) - P_{\text{bpm}}(c, t_k) - P_{\text{energy}}(c, t_k)$$

with default weights $w_{\text{local}} = 0.45$, $w_{\text{macro}} = 0.30$, and $w_{\text{art}} = 0.25$.

* **Similarity map:** Built from listening sessions, artist-to-artist transitions, albums, and artists in my library (on my server, about 600 sessions and 4,000+ artist transition pairs). `TruncatedSVD` turns this into a 32-dimensional vector for every track, so songs with no play history can still be recommended.
* **Two reference points:** Each candidate is compared to the starting song and the current song, which keeps the mix from drifting.
* **Tempo (counting half-time and double-time):**
  $$\Delta_{\text{BPM}} = \min(|BPM_c - BPM_{t_k}|, |BPM_c - 2 \cdot BPM_{t_k}|, |2 \cdot BPM_c - BPM_{t_k}|)$$
  A gentle penalty applies only above a ±10% difference.
* **Key (Camelot wheel):**
  * Same or relative key ($8A \leftrightarrow 8B$): $+0.20$
  * Adjacent key ($8A \to 9A$): $+0.12$
  * Three or more steps apart: $-0.25$
* **Variety (Gumbel-Top-$k$ sampling):**
  * Without this, the same starting song always produced exactly the same mix.
  * A small amount of random noise ($\tau = 0.20$) is added only to candidates above a minimum score.
  * Strong matches still tend to come first, but each mix is a little different. Poor matches stay below the cutoff.
* **Repetition and duplicates:**
  * At most 2 songs per artist in a queue by default.
  * Extra penalties for the same artist playing back to back.
  * Fuzzy matching removes the same song appearing on both an original album and a compilation.

## 5. Audio analyzer

Only a small number of my tracks had BPM tags, and none had key information, so `analyzer.py` was added:

* **How it works:** `aubio` estimates the tempo. A chromagram compared against Krumhansl–Schmuckler key profiles estimates the key, which is then converted to a Camelot code (1A–12B).
* **Speed on my machine:** About 12–15 tracks per second with 6 CPU workers, so my ~6,400-track library took about 7 minutes.
* **No restart needed:** The server checks `features.db` about every 15 seconds and picks up new results automatically.

## 6. A setup issue I ran into

### The "Shape of You" mix that made no sense
During early testing I started a mix from *Shape of You* (Ed Sheeran) in Amperfy and got a completely unrelated queue. Navidrome's logs showed that it couldn't reach the service:

```text
navidrome: [AudioMuse] Calling similar_tracks API: http://<server-ip>:8001/api/similar_tracks?...
navidrome: [AudioMuse] ERROR: HTTP request failed: dial tcp <server-ip>:8001: connect: connection refused
```

The test server was running in an isolated environment Navidrome couldn't reach, so Navidrome fell back to its own default behavior.

### What fixed it for me
1. Stopped my previous AudioMuse-AI containers so they wouldn't conflict on the same ports.
2. Installed the service as a regular systemd service on the host.
3. Had `server.py` listen on both ports **8000** and **8001**, so either URL works in the plugin settings.

## 8. Quick reference

### Managing the service
```bash
# Check status
systemctl status navidrome-autoplay

# Restart
systemctl restart navidrome-autoplay

# Follow the logs
journalctl -u navidrome-autoplay -f
```

### API endpoints
* `GET /health` or `GET /api/status`: Health check and basic statistics.
* `GET /api/similar_tracks?item_id=<id>&n=10&eliminate_duplicates=true`: Song recommendations.
* `GET /api/similar_artists?artist=<name_or_id>&count=10`: Related artists.
* `GET /api/find_path?start_song_id=<id>&end_song_id=<id>&count=5`: A short path of songs connecting two tracks.
* `GET /api/analysis_status`: How much of the library has been analyzed.
* `POST /api/reload`: Reload the database and rebuild the similarity map after adding music.
