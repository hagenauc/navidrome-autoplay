# Ideas: A Lightweight Autoplay / Similar Songs Approach for Navidrome

**Status:** Just an idea, shared for discussion  
**Related discussion:** [Navidrome Discussion #4332 ("Song similarity and automatic playlist generation")](https://github.com/navidrome/navidrome/discussions/4332)  
**Example implementation:** [navidrome-autoplay (GitHub)](https://github.com/hagenauc/navidrome-autoplay)

> [!NOTE]
> I'm a Navidrome user, not a contributor, and this is a personal hobby project. All of its code and documentation, including this note, were generated by an AI coding assistant while I guided it and tested it on my own server. I'm sharing it only in case some of the ideas are helpful. I'm not asking anyone to adopt it, and I fully understand if it doesn't fit Navidrome's plans or priorities.

---

## 1. Why I'm sharing this

Navidrome is a wonderfully lightweight, self-contained music server, and I really appreciate the work that goes into it. I wanted Instant Mix on my own library to behave a bit more like what I knew from streaming services, so I put together a small companion service. It works with the existing AudioMuse-AI Navidrome plugin.

While using it, I noticed a few things that mattered for my library:
* My library mixes Austrian/German music (Volksmusik, Schlager, Austropop) with pop, rock, and country. Purely acoustic similarity didn't always keep songs from the same "scene" together.
* When each song is chosen only by comparing it to the previous one, a mix can slowly drift somewhere unrelated.
* Starting a mix from the same song always gave exactly the same queue, and I wanted a bit of variety.

The approach borrows a few ideas from public descriptions of how Spotify and Apple Music handle autoplay: comparing to both the starting and the current song, mixing in a little randomness, and preferring compatible tempos and keys.

**What I saw on my own setup (about 6,400 tracks):** around 110 MB of memory, roughly 30 ms per 100-song mix, and about 7 minutes to analyze the whole library on 6 CPU cores. These are informal observations from one machine, not careful benchmarks.

## 2. How it works (briefly)

```
                       [ Navidrome / Subsonic client ]
                                     │
                                     ▼ (Instant Mix / Autoplay)
                         [ Subsonic getSimilarSongs2 ]
                                     │
                                     ▼
        ┌────────────────────────────────────────────────────────┐
        │                  Navidrome Autoplay                    │
        │                                                        │
        │  1. Similarity map of the library (TruncatedSVD)       │
        │  2. Compare to starting song + current song            │
        │  3. Keep within the same musical "scene"               │
        │  4. Tempo and key matching                             │
        │  5. A little randomness for variety                    │
        │  6. Artist limits and duplicate removal                │
        └────────────────────────────────────────────────────────┘
                                     │
                                     ▼
                          [ Queue of up to 100 songs ]
```

### A. A similarity map that covers the whole library
In my library, most songs have never been scrobbled or added to a playlist. To still have something to go on, tracks are connected through:
* **Same album** ($w=1.5$)
* **Same artist** ($w=0.8$)
* **Similar scene / artist name tokens** ($w=0.5$ – $2.0$), e.g. *Zillertal*, *Ambros*, *Ötzi*
* **Scrobbles and playlists**, weighted by how close together songs were played ($w = 1.0 / \Delta t$)

`TruncatedSVD` turns this into a 32-dimensional vector for every track, including ones with no play history.

### B. Two reference points
For candidate track $c$ and session history $H = [t_1, t_2, \dots, t_k]$, where $t_1$ is the starting song:

$$\text{Score}(c) = w_{\text{local}} S_{\text{svd}}(c, t_k) + w_{\text{macro}} S_{\text{svd}}(c, t_1) + w_{\text{art}} S_{\text{artist}}(c, t_k) + \text{Affinity}(c) - \text{Penalties}$$

with default weights $0.45$, $0.30$, and $0.25$. The starting song keeps the overall mood, and the current song keeps the next step smooth.

### C. A little variety (Gumbel-Top-$k$ sampling)
A small amount of noise ($\tau = 0.20$) is added only to candidates above a minimum score:

$$S'_c = S_c + \tau \cdot g_c, \quad g_c = -\ln(-\ln(U_c)), \; U_c \sim \text{Uniform}(0, 1)$$

Strong matches still tend to come first, but each mix comes out a little different. Poor matches aren't affected.

### D. Tempo and key
* **Camelot wheel:** same or relative key $+0.20$, adjacent key $+0.12$, three or more steps away $-0.25$.
* **Tempo, counting half-time and double-time:**
  $$\Delta_{\text{BPM}} = \min(|BPM_c - BPM_{t_k}|, |BPM_c - 2 \cdot BPM_{t_k}|, |2 \cdot BPM_c - BPM_{t_k}|)$$

## 3. Possible ways this could fit into Navidrome

I don't know Navidrome's internals well, so please treat these as loose thoughts from a user rather than a plan.

### Option A: In Navidrome itself (Go)
None of the math needs heavy frameworks, so in principle something similar could be written in Go:
1. Build the similarity map from the existing `scrobbles` and `playlist_tracks` data, possibly with `gonum.org/v1/gonum/mat` for the SVD.
2. Track the starting and current song in memory.
3. Use existing `media_file.bpm` and `media_file.initial_key` tags for tempo and key.
4. Use `math/rand/v2` for the variety step.

This might fit Navidrome's single-binary approach, but the maintainers would know far better than I would.

### Option B: As a plugin (`.ndp`)
It could also be packaged as an Extism WASM plugin, either with the scoring logic inside the plugin or talking to a small companion service like this one.
